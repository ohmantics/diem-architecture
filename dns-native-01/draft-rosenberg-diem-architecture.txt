             Digital Emblems - Architectural Considerations
                draft-rosenberg-diem-architecture-latest

Abstract

   This document describes an architecture for digital emblems in which
   emblems are authenticated, typed metadata about assets, published in
   the DNS and protected by DNSSEC.  A single architecture serves many
   use cases.  Use cases differ in the shape of their metadata, which is
   described by profiles, rather than in their transport or trust
   machinery.  The document illustrates the architecture with a strawman
   encoding (an EMBLEM resource record carrying a deterministic CBOR map
   with registered, typed keys) and with worked examples drawn from
   International Humanitarian Law, logistics and customs, and diplomatic
   pouches.

1.  Introduction

   The DIEM working group is developing standards for digital emblems: a
   means for associating metadata with physical or virtual assets, often
   to indicate what treatment they should receive under some normative
   framework [CHARTER] [DIEM-REQS].  The use cases range from
   protections under International Humanitarian Law (IHL) to trade and
   logistics labeling, environmental designations, and diplomatic
   privileges.

   The central claim of this document is that these use cases differ
   mainly in _what they say_, not in _how it is said_. A hospital, a
   pallet of smartphones, and a diplomatic pouch all need an identifier
   that a validator can learn, a way to retrieve statements about the
   identified asset, assurance that the statements come from the party
   entitled to make them, and in some cases confidentiality, third-party
   authorization, or offline operation.  These are architectural
   concerns that can be addressed once.  What differs between use cases
   is the dictionary of facts being conveyed, and that is the job of a
   profile.

   An architecture document would ordinarily stay clear of protocol
   detail.  In DIEM's case, several participants (including the author)
   have found it difficult to reason about the architecture without
   thinking concretely about the protocol it implies.  This document
   therefore includes a strawman encoding (Section 14).  The strawman is
   illustrative: it exists to show that the architecture can be realized
   with existing DNS machinery and to give the working group something
   concrete to criticize.  Normative protocol specifications would
   follow in separate documents.

   This revision substantially reworks draft-rosenberg-diem-
   architecture-00 in response to working group feedback, particularly
   from DNS practitioners who urged that DIEM lean on DNSSEC rather than
   duplicate its integrity guarantees at the application layer.

2.  Conventions and Definitions

   This document uses the terms "(digital) emblem", "asset", "emblem
   issuer", "authorizing entity", "validator", and "validation" as
   defined in [DIEM-REQS].  It also uses the following terms:

   Profile:  The schema for the metadata an emblem conveys for a
      particular use case or industry: which keys appear, what type each
      value has, which keys are required, which are confidential, and
      how a validator should interpret them.  A profile is a description
      of data.  It is not a separate protocol stack, and different
      profiles share the same discovery, trust, and encoding machinery.
      One profile may serve several use cases (for example, a
      consignment profile used by both customs and recyclers), and one
      asset may carry emblems from several profiles.

   Emblem name:  The DNS owner name at which an asset's emblem records
      are published.

   Emblem record:  A DNS resource record conveying all or part of an
      emblem.  In the strawman, the EMBLEM RRType.

   Facet:  A subset of an emblem's data that is retrieved, cached, or
      signed independently of the rest, and is therefore published as
      its own RRset (a separate RRType, or a separate owner name).

   Key:  A registered identifier for one property in an emblem's
      dictionary, with a defined value type.

   Code list:  An externally maintained controlled vocabulary (for
      example, ISO 3166-1 country codes [ISO3166] or UNECE
      Recommendation 20 unit codes) used as the type of a key's value.

   Endorsement:  A statement by an authorizing entity that an emblem
      issuer is authorized to issue emblems of a given profile or scope.

   Offline bundle:  A self-contained serialization of emblem RRsets,
      their RRSIGs, and the DNSSEC chain needed to validate them,
      suitable for transfer without network access.

3.  Design Principles

   One architecture, many profiles:  Use cases vary the data, not the
      plumbing.  A validator that understands discovery, DNSSEC
      validation, and the common encoding can retrieve and authenticate
      any emblem, even one whose profile it cannot interpret.  This
      avoids a family of disjoint per-use-case systems, which would
      multiply implementation cost and fragment the validator base.

   Use the DNS for what it already does:  DNSSEC [RFC4033] [RFC4034]
      [RFC4035] [RFC9364] provides data origin authentication and
      integrity for RRsets, authenticated denial of existence, and a
      delegation model that maps naturally onto organizational
      boundaries.  DIEM should rely on these rather than re-create them
      with application-layer signatures.  Application-layer cryptography
      is reserved for what DNSSEC does not provide: confidentiality,
      cross-zone endorsement, and offline transfer.

   Typed data:  Every key has a registered type, and every value can be
      checked against it.  A validator must be able to tell malformed
      data from well-formed data, and to tell one property from another
      without reading free text.  Externally maintained code lists are
      value types bound to keys, not free-standing records.

   Query granularity equals record granularity:  Data that a validator
      needs to retrieve independently, or that changes on a different
      schedule, belongs in its own RRset.  Data that is always used
      together belongs in one record.  The DNS offers projection (by
      owner name and type) but no predicates, so the record layout is
      the query model.

   Encryption, not audience-dependent answers:  Restricted fields are
      encrypted inside signed records, so that every validator receives
      the same cacheable, signed answer and only authorized validators
      can read the restricted parts.  Serving different answers to
      authenticated clients is possible as a deployment option but is
      not the architectural primitive (see Section 9).

   Neutral about normative frameworks:  The architecture conveys
      statements; it does not adjudicate them.  Legal meaning (what an
      emblem entitles an asset to, who may authorize it) lives in
      profile data and in the frameworks that profiles reference.

4.  Roles and Trust

   The architecture has two active roles on the wire:

   *  An _emblem issuer_ publishes emblem records in a DNS zone it
      controls (directly, or through a contracted DNS operator).

   *  A _validator_ retrieves emblem records and validates them.

   An _authorizing entity_, where a profile requires one, participates
   by publishing endorsements in its own zone or by signing endorsements
   that travel with the emblem (Section 8).  It does not need to be
   online during validation.

     authorizing entity       emblem issuer          validator
     (state, treaty body,     (hospital, maker,      (armed forces,
      NPPO, ministry ...)      shipper, MFA ...)      customs, recycler)
            |                        |                      |
            | endorsement            | emblem records       |
            | (own zone, or          | (DNSSEC-signed,      |
            |  detached signature)   |  maybe delegated)    |
            v                        v                      |
     +--------------------------------------------+         |
     |                    DNS                     |<--------+
     | root -> TLD -> issuer zone -> emblem names |  query and
     +--------------------------------------------+  validate

                              Figure 1: Roles

   Trust in an emblem's content derives from the DNSSEC chain of trust
   to the zone that publishes it.  A validated EMBLEM RRset establishes
   that the holder of the zone's signing keys published that data, and
   nothing more.  Whether that zone holder is entitled to make the
   statement is a separate question, answered by endorsements where a
   profile requires them and otherwise by the validator's own knowledge
   (a customs officer knows which shippers they deal with).

   This model has a single technical root (the DNS root zone), but it
   does not create a central authority over emblems.  No party needs
   another's permission to publish emblems in its own zone, and
   authorizing entities operate independently of one another.  Profiles
   whose frameworks require it can place their own authorizing entities
   wherever the framework places them.

   Three consequences deserve emphasis:

   *  DNSSEC authenticates the zone, not the real-world identity behind
      it.  A lookalike domain (for example, one using Cyrillic "a"
      (U+0430) in place of Latin "a" (U+0061)) validates just as well as
      the genuine one.  Profiles should carry cross-check identifiers (a
      GTIN, a container number, a registration number) that a validator
      can compare against the physical or contextual evidence in front
      of it, and endorsements help where a third party vouches for the
      issuer.

   *  In practice, many signed zones are signed by contracted operators
      rather than by registrants.  The architecture treats the zone's
      signing keys as the issuer's voice, so issuers should choose
      operators accordingly.

   *  The architecture depends on DNSSEC deployment.  An issuer needs a
      signed chain from the root to its emblem names, so an issuer whose
      TLD is not signed must publish under one that is.  Validators must
      validate themselves or use a validating resolver they trust over a
      secure channel.

5.  Naming and Discovery

5.1.  Identifying the Asset

   Assets are identified by domain names.  How a validator learns an
   asset's name depends on the asset:

   *  For digital services, the asset's own name is usually already
      known (the validator is about to connect to it).

   *  For physical assets, the name is conveyed out of band: printed, in
      a QR code, in an NFC or RFID tag, or in shipping documents.  A URI
      scheme for emblem names would let general-purpose scanners
      recognize them; this is an open question.

   *  Some assets are found by other means (a location, a registry
      listing), and [DIEM-REQS] notes asset identifier discovery as a
      possible future extension.

5.2.  Choosing Emblem Names

   The architecture does not constrain emblem names.  An issuer may
   publish emblems at an asset's own name or at any name in a zone it
   controls, and validators use whatever emblem name they are given;
   they do not construct names from a fixed pattern.  Where a profile
   derives an emblem name from an asset's name (for example, for network
   services whose names validators already know), that profile defines
   the derivation.

   As an operational recommendation, issuers should consider placing
   emblem names under a dedicated label, _diem in this document's
   examples, because it permits a zone cut:

   example.org.                  NS   ordinary-dns.example.net.
   _diem.example.org.            NS   ns1.diem-provider.example.
                                 DS   ...

   With a cut at _diem, the issuer's ordinary DNS service needs no
   knowledge of DIEM.  Emblem names are served by an authoritative
   server specialized for emblems, which may be backed by an asset-
   management or inventory system rather than a zone file, and which may
   have different security and signing arrangements.  Resolvers need no
   DIEM awareness at all; they cache and validate emblem records like
   any other RRType.

   Below the cut, the issuer arranges names however suits its inventory.
   Hierarchical names express hierarchical assets (Section 7), and
   wildcards [RFC4592] can cover classes of assets that share all of
   their data.  Wildcards have limits: they do not match names that
   exist (including empty non-terminals), and because every name under a
   wildcard appears to carry an emblem, they must not be used where the
   existence of an emblem for a particular item (such as a serial
   number) is itself meant to be evidence.

5.3.  Retrieval

   A validator retrieves an emblem by querying for the relevant RRType
   at the emblem name, and validates the response with DNSSEC.  Where a
   profile places facets in separate RRsets (Section 6.4), the validator
   retrieves only the facets it needs.  A validator that receives
   NXDOMAIN or NODATA with a valid denial-of-existence proof learns
   authoritatively that no emblem (or no such facet) is published.

   DNS transports are interchangeable here.  Large responses use TCP or
   encrypted transports (DoT [RFC7858], DoH [RFC8484], DoQ [RFC9250]);
   the encrypted transports also provide confidentiality between the
   validator and its resolver.

6.  Data Model

   An emblem is a dictionary: a set of key/value pairs, in which values
   may themselves be arrays or dictionaries.  Every emblem identifies
   the profile that defines its keys.

6.1.  Keys and Types

   Keys are drawn from registries.  A small set of common keys applies
   to all profiles (profile identifier, the FQDN of the marked asset,
   cross-check asset identifiers, validity period, issuer display name).
   The charter requires that emblems explicitly identify the marked
   asset by FQDN [CHARTER], so the asset key is required even when the
   emblem is published at the asset's own name.  Each profile defines
   additional keys.  Every key definition specifies the value's type,
   preferably in CDDL [RFC8610].

   A validator checks each value against its key's type.  A value that
   does not match its type is an error, not a curiosity to be displayed.
   Unknown keys may be ignored, unless the emblem marks them as critical
   (in the manner of the COSE "crit" header parameter [RFC9052]), in
   which case a validator that does not understand them must not rely on
   the emblem.  This lets profiles evolve without breaking old
   validators, while still allowing an issuer to say "do not act on this
   emblem unless you understand all of it".

6.2.  Value Types

   The following value types cover the use cases identified so far:

   +===================+===============================================+

   |                   | and mantissa), never binary floating point    |

   | quantity          | decimal plus a unit code from UNECE           |
   |                   | Recommendation 20 [UNECE20]                   |
   +-------------------+-----------------------------------------------+
   | monetary amount   | decimal plus a currency code from ISO 4217    |
   |                   | [ISO4217]                                     |
   +-------------------+-----------------------------------------------+

                            Table 1: Value types

   Two distinctions from
   [I-D.woodcock-faltstrom-external-registry-rrtypes] are worth
   adopting: a value that is _not applicable_ (the key is absent)
   differs from a value that _exists but is unknown to the issuer_ (the
   key is present with an explicit "unknown" marker), and an issuer's
   signed assertion of ignorance is itself meaningful.

6.3.  External Code Lists as Value Types

   Much of the data that emblems carry is already standardized
   elsewhere: country codes, currency codes, units of measure, location
   codes, commodity classifications, dangerous goods numbers.  DIEM
   should use these code lists rather than reinvent them, and should not
   mirror them into IANA registries.  On both points this document
   agrees with [I-D.woodcock-faltstrom-external-registry-rrtypes], which
   argues them well.

   Where this document differs is in _where the code list attaches_. In
   the external-registry RRTypes, a record names a code list (for
   example, "ISO 3166-1") and carries a code, an optional quantity, and
   an optional free-text descriptor.  The property that the code
   describes (whether "QA" is a flag state, a place of incorporation, or
   a country of origin) is carried only in the descriptor, which
   receivers must not interpret.  Two records about the same asset that
   use the same code list are therefore indistinguishable to software.

   In this architecture, the code list is the _type_ of a key:

   / external-registry pattern (illustrative): meaning only in text /
   ISO 3166-1 - QA "flag state"
   ISO 3166-1 - US "state of incorporation"

   / typed keys: the key carries the meaning, the code list the type /
   { "flag-state": "QA", "incorporated-in": "US" }

                     Figure 2: Where the meaning lives

   A key definition says "the value is an ISO 3166-1 alpha-2 code", so a
   validator can reject "Q4" or "qa" (the codes are compared verbatim,
   as in the external-registry draft), and software can act on "flag-
   state" directly.  The alternative, recovering the property by parsing
   descriptor strings such as "flag state", is error-prone: descriptors
   are unconstrained text, so the same property can be written in many
   ways, in any language, abbreviated, or misspelled, and different
   parser implementors may interpret the strings differently.  Where a
   key admits values from more than one code list, the value carries a
   small code-list identifier alongside the code.  The registry of code-
   list identifiers references external lists without copying their
   contents.

   This approach also reaches code lists that do not fit a one-RRType-
   per-maintainer pattern.  The OPCW use case in [DIEM-REQS] needs
   Chemical Abstracts Service registry numbers, IUPAC names, GHS hazard
   pictograms, and UN dangerous goods numbers [UNMODELREGS]; the
   logistics example below needs Harmonized System codes [HS] and ISPM
   15 treatment codes [ISPM15].  Each of these becomes a value type that
   keys can use, with no new RRType per maintainer.

6.4.  Facets: Signed Once, Signed Often

   Some emblem data never changes for the life of the emblem (a serial
   number, a hazard classification, a legal designation).  Some changes
   constantly (the location of a container in transit). draft-rosenberg-
   diem-architecture-00 described this as "signed" versus
   "informational" fields.  In a DNS-native design, the distinction maps
   onto RRsets:

   *  Static facets are published in RRsets that can be signed offline
      and given long TTLs.

   *  Dynamic facets are published in separate RRsets with short TTLs.
      Because any key in a zone's DNSKEY RRset can sign any RRset in
      that zone, an online signing key in the same zone could also forge
      the static data.  Dynamic data that must be signed online is
      therefore placed in a separate, online-signed zone (for example,
      one shared zone for all of an issuer's dynamic facets), so the
      static data remains under offline keys.

   Facets are also the unit of retrieval.  A recycler that only needs
   the battery chemistry does not need to fetch the declared customs
   value, and a customs officer does not need recycling instructions.
   Each facet is either a distinct RRType at the emblem name (a LOC
   record for position, a URI record [RFC7553] for a link to
   documentation) or a distinct owner name below it.

   This replaces the application-layer hashing of the -00 draft.  DNSSEC
   already signs each RRset; a validator that retrieves a facet gets
   integrity for exactly that facet.

7.  Hierarchy and Composition

   Physical assets nest: devices in cartons, cartons on pallets, pallets
   in containers, containers on ships.  Different parties attest to
   different levels.  The architecture expresses this in two ways:

   *  Within one issuer's zone, by DNS hierarchy.  An emblem name for a
      product class can have child names for individual items, so that
      class-wide data (model, hazard classification) is published once
      and item-specific data (serial number) is published per item.

   *  Across issuers, by reference.  A shipper's consignment emblem
      refers to the manufacturer's emblems by domain name.  Each
      referenced emblem is validated through its own zone's DNSSEC
      chain.  Where the referencing party wants to fix exactly what it
      saw at the time (for example, a declaration to customs), the
      reference also carries a digest of the referenced RRset.

   A validator walks as far as its task requires.  A customs officer may
   validate only the shipper's consignment emblem; a recycler may
   validate a single device's battery facet back to the manufacturer; an
   audit may walk everything.  Full walks of large consignments involve
   many queries, which caching, wildcards for homogeneous items, and
   offline bundles all mitigate.

8.  Authorization and Endorsement

   Some profiles require that an issuer be authorized by a third party:
   a state authorizing use of a protective emblem under IHL, a national
   plant protection organization authorizing a pallet producer to apply
   the ISPM 15 mark, a treaty secretariat recognizing a designated site.
   DNSSEC proves who published an emblem, not who authorized it.
   Endorsement fills that gap, and this document sketches two
   complementary forms.

   Published endorsement:  The authorizing entity publishes, in its own
      DNSSEC-signed zone, a record naming the endorsed issuer and the
      scope of the endorsement (profile, permitted purposes, validity
      period).  For example,
      hospital.example._endorse.health.gov.example might carry an
      ENDORSE record listing the protective purposes the ministry has
      authorized for hospital.example.  Validation is pure DNSSEC, and
      revocation is removal (bounded by TTL and signature lifetime).
      The cost is an extra query, directed at the authorizing entity's
      zone.

   Detached endorsement:  The authorizing entity signs a statement
      binding the issuer's zone (or the issuer's DNSKEY) to a scope,
      using a key published in the authorizing entity's own signed zone.
      The issuer publishes this signed statement inside or alongside its
      emblem, together with the DNSSEC chain for the authorizing
      entity's key (as in an offline bundle, Section 10).  A validator
      that receives this, or that already holds the authorizing entity's
      key, needs no query to the authorizing entity at validation time.
      A detached endorsement cannot be recalled once issued, so it
      should be short-lived and renewed for as long as the authorization
      stands.  This suits profiles that require undetectable validation
      or offline operation.  The endorsement chains, purpose
      constraints, and accountability mechanisms of
      [I-D.linker-diem-adem-core] fit naturally here, as does an
      optional transparency-log commitment for authorizing entities that
      want to make key equivocation detectable.

   A profile chooses which forms it accepts.  Both keep the authorizing
   entity's trust anchored in a zone it controls, so no global registry
   of authorities is needed.

9.  Confidentiality and Selective Disclosure

   Some emblem data is restricted: a consignment's declared value, the
   identity of a diplomatic courier, an issuer's internal forensic data.
   [DIEM-REQS] anticipates selective disclosure.

   The architectural primitive is encryption of values inside signed
   records.  An encrypted value is a COSE [RFC9052] encryption structure
   (COSE_Encrypt0 for a single recipient, COSE_Encrypt with recipient
   structures where several parties, such as origin and destination
   customs, need access), with keys distributed as the profile specifies
   (for example, using HPKE [RFC9180] [I-D.ietf-cose-hpke] to a public
   key that a customs authority publishes in its own zone).  DNSSEC
   signs the ciphertext, so integrity covers restricted fields even for
   validators that cannot read them.  This resolves an open question
   from the -00 draft (how encrypted subrecords participate in integrity
   protection): the signature covers what is published, which is the
   ciphertext.

   The alternative of authenticated DNS views, in which the server
   authenticates the client and returns different data to different
   audiences, is not recommended as the general mechanism:

   *  It identifies validators to issuers' servers, which is
      unacceptable where inspection patterns are sensitive (and fatal to
      undetectable validation).

   *  Answers that differ per client cannot be shared through resolver
      caches, so the restricted tier becomes an application API with DNS
      framing.

   *  Standardizing mandatory client identification for DNS lookups
      creates a precedent that could be misused well beyond DIEM.

   Profiles may still use authenticated access where audit of who looked
   is itself a requirement, but should do so knowingly.

   Confidentiality also covers existence.  Where the mere existence of
   an emblem name is sensitive, issuers use unguessable labels and a
   denial-of-existence method that does not reveal them.  Plain NSEC
   allows zone walking and would expose such labels.  Compact denial of
   existence [RFC9824] reveals nothing but requires online signing;
   offline-signed zones can use NSEC3 [RFC9276], whose hashed names
   resist enumeration when the labels themselves have high entropy.

10.  Offline and Constrained Validation

   [DIEM-REQS] requires that the architecture not assume Internet
   access.  DNSSEC data is self-authenticating: an RRset, its RRSIG, and
   the chain of DNSKEY and DS records up to a trust anchor can be
   validated anywhere, by anyone holding the root trust anchor and a
   clock.

   An offline bundle serializes exactly that, following the pattern of
   the TLS DNSSEC chain extension [RFC9102] and the CHAIN query
   [RFC7901].  A full chain from the root is typically a few kilobytes
   (less for zones using ECDSA or Ed25519), so a bundle fits in a large
   QR code, a high-capacity tag, or an accompanying document, and can be
   validated at a disconnected port or in the field.  Its validity is
   bounded by the shortest RRSIG validity period it contains, which also
   bounds how long a removed emblem can be replayed.  That includes the
   signatures of the root and TLD zones, which the issuer does not
   control and which typically last one to three weeks, so bundles have
   a limited shelf life and must be refreshed for long journeys.

   Offline bundles take over the role that application-layer signed
   objects (such as signed CBOR) played in earlier thinking, without
   introducing a second signature system.

11.  Lifecycle, Removal, and Forensics

   Removal:  Some profiles require that an emblem be removable
      ([DIEM-REQS]).  Removing the records stops new validators from
      finding them, but signed copies remain valid until their RRSIGs
      expire, and caches may hold them until their TTLs expire.
      Profiles that need prompt removal should use short signature
      validity periods and TTLs, which in practice means online signing,
      and which limits the shelf life of offline bundles accordingly.
      Profiles should also be candid in their threat models that the DNS
      is not forgetful: passive DNS collectors may retain records
      indefinitely, which matters for the "learn after the fact" aspect
      of removability.

   Archival:  Removal from the DNS is not deletion.  Most use cases
      expect the issuer to archive emblems, with lifespan rules set by
      the profile.  Some archived data is public forensic record; some
      is internal (for example, the identity of the staff member who
      created a record) and may be published only in encrypted form or
      not at all.

   Proof of presence:  A validated DNSSEC response is a portable, third-
      party-verifiable record that the zone's key signed a given emblem
      with a validity period covering a given time.  A validator that
      retains the response (with the DNSKEYs then in effect) holds
      evidence supporting Level 1 proof of presence in the terms of
      [DIEM-REQS].  Level 2 (that a validator accessed the emblem) would
      need records of access, for example server-side logs where a
      profile accepts that access is observable, and Level 3 must come
      from the validator's own signed records; both are outside the DNS
      data itself.

12.  Undetectable Validation

   The IHL use case requires that validation be undetectable by the
   asset's operator ([DIEM-REQS]).  Several mechanisms contribute, and
   none is sufficient alone:

   *  Resolver mediation: an issuer's authoritative server sees queries
      from resolvers, not from validators.  Large shared resolvers and
      Oblivious DoH [RFC9230] enlarge or obscure the population of query
      sources.  EDNS Client Subnet [RFC7871] works against this;
      validators should use resolvers that do not send it, or opt out
      with a source prefix length of zero.

   *  Limiting other observers: encrypted transports protect the path to
      the resolver, and QNAME minimisation [RFC9156] keeps parent zones
      from learning the full name.  Neither hides the query from the
      issuer's own authoritative server.

   *  Caching: a cached answer generates no query at all.

   *  Self-contained answers: if everything needed for validation
      (including endorsements) arrives in one response, no follow-up
      query to the issuer or authorizing entity reveals interest.

   *  Query indistinguishability: if the query that retrieves an emblem
      is one that ordinary clients make anyway, retrieving the emblem
      reveals nothing.  [STEELE-DEMO] carries the emblem in a parameter
      of the asset's HTTPS record [RFC9460]; [I-D.linker-diem-adem-dns]
      has authoritative servers include emblem records in the additional
      section of any response for the asset's name.  Both are
      interesting.  Both require emblem data in the asset's own zone,
      which rules out delegating emblems to a separate server through a
      zone cut.  The additional-section approach also requires modified
      authoritative server behavior, and recursive resolvers commonly
      discard additional-section records that were not requested (in
      line with the trust ranking of RFC 2181), so it is unlikely to
      work through today's resolvers without changes there as well.  It
      deserves careful review by DNS operators.

   A profile that requires undetectable validation must state its threat
   model ([DIEM-REQS]) in terms of which of these it relies on.

14.  Strawman Encoding

   This section is illustrative.  It sketches one way to realize the
   architecture so that the working group can evaluate it; it is not a
   specification.

14.1.  The EMBLEM RRType

   The EMBLEM RRType carries one emblem dictionary (or one facet of one)
   as RDATA.

   *  The RDATA is a single CBOR [RFC8949] map using core deterministic
      encoding (Section 4.2.1 of [RFC8949]).  Deterministic encoding
      fixes the serialization but not application-level equivalence, so
      the encoding must also fix canonical forms (for example, decimal
      mantissas without trailing zeros, integer epoch seconds) for equal
      emblems to have equal wire representations.

   *  Map keys are small integers from a "DIEM Emblem Keys" registry
      (common keys) or from the key space of the profile named in the
      map.  Text names are used in this document for readability.

   *  Key 1, "profile", is required.

   *  Decimal values use CBOR tag 4 (decimal fraction); timestamps use
      tag 1; language-tagged text uses tag 38; URIs use tag 32;
      encrypted values are COSE_Encrypt0 (tag 16) or COSE_Encrypt (tag
      96); a value that exists but is unknown to the issuer is the CBOR
      simple value undefined.

   *  RDATA contains no compressible domain names, so the type is
      compatible with unknown-type handling [RFC3597].  Domain-name
      references are carried as text, normalized for comparison and
      digests (A-labels, lowercase, without a trailing dot).

   *  The presentation format would be the generic \# length hex form of
      [RFC3597], with CBOR diagnostic notation for human display.

   Why a CBOR map rather than SVCB-style key/value parameters [RFC9460]?
   Both preserve the dictionary model.  CBOR brings typed values,
   nesting, decimal fractions, language tags, and COSE encryption
   without new definitions, and it aligns with CBOR-based work already
   presented to the working group [I-D.linker-diem-adem-core]
   [STEELE-DEMO].  The cost is that zone-file tooling would need a CBOR-
   aware presentation format to be friendly.

   Why not one opaque blob per asset?  Because DNSSEC signs per RRset,
   packing everything into one record forfeits independent retrieval,
   independent TTLs, and the static/dynamic split of Section 6.4.
   Profiles should split emblems into facets along the lines that
   validators actually query.

   Size needs attention at two levels.  Individual records vary: device-
   level emblems like those below are on the order of 100 octets, but a
   consignment emblem with transport references and several encrypted
   fields can exceed a typical UDP response and will arrive over TCP or
   an encrypted transport.  Aggregates matter more: a consignment of
   1,400 devices implies 1,400 item emblems, and validators should not
   have to fetch them all.  Class-level data is published once,
   consignments refer to items by digest rather than listing them, and
   validators sample individual items or use an offline bundle prepared
   for the consignment.

14.2.  Companion RRTypes

   Existing RRTypes serve some facets directly: LOC [RFC1876] for point
   positions, URI [RFC7553] for references to documentation, TLSA
   [RFC6698] where an emblem is bound to a TLS service.  A QTY-style
   RRType for typed quantities was proposed in
   [I-D.bwbh-digital-emblem-model] and could be revived for profiles
   that query quantities independently.

   New types would be needed for endorsements (ENDORSE) and possibly for
   areas (polygons), which LOC does not express.  All of these, like
   EMBLEM, need only Expert Review for allocation [RFC6895].

15.  Example Use Cases

   The following examples are sketches.  Names, keys, and values are
   illustrative.  Emblem dictionaries are shown in CBOR diagnostic
   notation with text keys, using the elision ... of
   [I-D.ietf-cbor-edn-literals] for long values.  Country codes
   beginning with "X" are user-assigned placeholders.

15.1.  IHL: A Hospital and Its Digital Services

   Example General Hospital operates a patient records system at
   records.hospital.example.  Under IHL, a medical unit entitled to
   protection may display the red cross, red crescent, or red crystal
   with the authorization of the competent authority, and Additional
   Protocol I already provides distinctive signals, including radio
   signals and electronic identification, chiefly for medical transports
   (Article 18 and Annex I, Chapter III of [API]).  A digital emblem
   extends this to the hospital's network services.

   Issuer and authorization:  The hospital is the issuer.  The ministry
      of health of its state, as the competent authority, endorses the
      hospital for the protective use of the emblem.  Because validators
      must not reveal their interest, the hospital publishes a detached
      endorsement signed by the ministry inside its emblem, together
      with the DNSSEC chain for the ministry's key, so validation
      requires no query to the ministry.

   Placement:  The asset is a network service, so its name is already
      known to anyone who would interact with it.  The hospital may
      publish at _diem.records.hospital.example (delegated to a provider
      that serves emblems), or use one of the query-indistinguishability
      techniques of Section 12 at the service's own name, as its
      profile's threat model dictates.

   / EMBLEM at _diem.records.hospital.example /
   {
     "profile": "ihl-protective",
     "purpose": ["protective-red-cross"],
     "asset":   "records.hospital.example",
     "valid":   [1(1793491200), 1(1801440000)],
     "issuer-name": 38(["en", "Example General Hospital"]),
     "endorsement": {                / detached, from the ministry /
       "by":    "health.gov.example",
       "scope": ["protective-red-cross"],
       "sig":   h'...',
       "chain": h'...'               / DNSSEC chain for ministry key /
     }
   }

   Validator:  A cyber unit planning operations queries through a large
      shared resolver, receives the emblem with its embedded endorsement
      in one response, validates the emblem with DNSSEC and the
      endorsement against the included chain, and finds that the asset
      is marked with protective use authorized by the named ministry.
      (With the chain embedded, the emblem is several kilobytes, so it
      arrives over TCP or an encrypted transport.)  What it does with
      that is a matter for IHL, not for the protocol.

   Removal:  If the hospital judges that the emblem increases its risk,
      it removes the records.  Its profile specifies short signature
      lifetimes and TTLs (hours, not weeks), which bounds replay of the
      removed emblem and implies that the hospital's emblem zone is
      signed online.

15.2.  Logistics and Customs: A Pallet of Smartphones

   A manufacturer ships 1,400 boxed smartphones on a wooden pallet.  A
   freight forwarder consolidates the pallet into a consignment.
   Customs at the destination, and eventually a recycler, need different
   subsets of the data.

   The manufacturer's zone holds class-level and item-level data:

   x1.models._diem.maker.example.              EMBLEM  (class: model X1)
   sn-35791a7c.x1.models._diem.maker.example.  EMBLEM  (one device)

   / EMBLEM at x1.models._diem.maker.example (static, offline-signed) /
   {
     "profile": "product-class",
     "asset":   "x1.models._diem.maker.example",
     "gtin":    "00614141999996",
     "model":   "X1",
     "dangerous-goods": {
       "un-number": "3481",  / Li-ion batteries in equipment /
       "class":     "9"
     },
     "battery-chemistry": "li-ion",
     "battery-energy": [4([-1, 185]), "WHR"],   / 18.5 watt-hours /
     "recycling": 32("https://maker.example/recycle/x1"),
     "origin":    "VN",
     "mid-us":    "VNEXAMAK123HAN",     / US manufacturer ID /
     "radio-auth": {"fcc-id": "2AEXAX1"},
     "components": [
       {"part": "battery-cell",
        "attestation": "cell.x1.supply._diem.maker.example",
        "digest": h'5e1b...'},
       {"part": "display",
        "attestation": "disp.x1.supply._diem.maker.example",
        "digest": h'c07a...'}
     ]
   }

   / EMBLEM at sn-35791a7c.x1.models._diem.maker.example /
   {
     "profile": "product-item",
     "asset":   "sn-35791a7c.x1.models._diem.maker.example",
     "serial":  "35791A7C",
     "made":    1(1790812800)
   }

   The hazardous materials, origin, and regulatory data is published
   once for the model, not 1,400 times.  A validator holding a device's
   emblem name finds class data by removing the leftmost label.  The
   manufacturer mirrors the attestations it holds for key components in
   its own zone, each with a digest of the original, so that a validator
   can trace components without contacting the component suppliers.

   The pallet carries the ISPM 15 mark [ISPM15], authorized by the
   national plant protection organization (NPPO) of the country where
   the mark was applied.  The pallet producer publishes the mark's data,
   and the NPPO endorses the producer (a published endorsement suffices
   here, since nobody needs to hide that they checked a pallet):

   / EMBLEM at p-20261031-0042._diem.pallets.example /
   {
     "profile":   "ispm15",
     "asset":     "p-20261031-0042._diem.pallets.example",
     "country":   "VN",          / ISO 3166-1 alpha-2 /
     "producer":  "000123",      / registration number from the NPPO /
     "treatment": "HT"           / heat treatment /
   }
   / ENDORSE at pallets.example._endorse.nppo.gov.example /

   The forwarder wraps everything in a consignment emblem at an
   unguessable name in its own zone (an NSEC3-signed zone, so the name
   cannot be enumerated), with live position in a shared online-signed
   zone:

   / EMBLEM at c-7f3k9q2m._diem.forwarder.example /
   {
     "profile":    "consignment",
     "asset":      "c-7f3k9q2m._diem.forwarder.example",
     "hs-code":    "851713",          / smartphones /
     "hts-us":     "8517130000",
     "origin":     "VN",
     "container":  "EXMU1234569",     / ISO 6346 /
     "seal":       "EX4471029",
     "packages":   [1, "PX"],         / UNECE Rec. 21: pallet /
     "gross-mass": [4([0, 725]), "KGM"],
     "transport": {
       "bill-of-lading":   "EXSC260098812",
       "carrier":          "EXSC",
       "vessel":           "EXAMPLE STAR",
       "voyage":           "042E",
       "port-of-lading":   "VNSGN",   / UN/LOCODE /
       "port-of-unlading": "USLAX"
     },
     "valuation":  16(...),           / encrypted to customs /
     "parties":    16(...),           / encrypted: seller, buyer, /
                                      / importer of record, bond, /
                                      / ship-to, consolidator,    /
                                      / stuffing location         /
     "contents": [
       {"emblem": "p-20261031-0042._diem.pallets.example"},
       {"emblem": "x1.models._diem.maker.example", "count": 1400,
        "items-digest": h'9a0c...'}   / digest of the item name list /
     ]
   }

   / LOC at c-7f3k9q2m._live._diem.forwarder.example /
   / (shared online-signed zone, TTL 300)              /

   The valuation is a dictionary of its own, encrypted so that only
   customs can read it.  Its plaintext uses monetary amounts (a decimal
   and an ISO 4217 code) and the commercial terms customs needs to
   determine the customs value:

   / plaintext of "valuation" /
   {
     "basis":      "transaction-value",
     "related-party": false,
     "incoterm":   "FOB",                   / ICC Incoterms rule /
     "invoice":    "INV-2026-10-4471",
     "unit-price": [4([-1, 4125]), "USD"],  / 412.50 /
     "quantity":   1400,
     "total":      [4([2, 5775]), "USD"],   / 577,500 /
     "freight":    [4([2, 32]), "USD"],     / 3,200 /
     "insurance":  [4([0, 1155]), "USD"],   / 1,155 /
     "additions":  []                       / no assists or royalties /
   }

   Customs:  The officer scans the consignment's code, validates the
      forwarder's emblem, and decrypts the valuation and parties with
      the customs authority's key.  The container and seal numbers,
      gross mass, and transport references tie the emblem to the
      carrier's manifest and to what is physically in front of the
      officer.  National requirements (here a US tariff number,
      manufacturer identification code, and radio equipment
      authorization) are keys like any other.  Because amounts are typed
      decimals with currency codes, software can check that unit price
      times quantity matches the total and the declared item count,
      compare the unit price with what is plausible for HS 8517.13 and
      model X1, and compute the customs value on the authority's own
      basis (adding freight and insurance where it values on a CIF
      basis).  The officer also checks the dangerous goods
      classification, optionally validates the pallet's ISPM 15 data and
      NPPO endorsement, and can follow the class emblem's component
      attestations where supply-chain tracing is required.  A retained
      copy of the validated response records exactly what the forwarder
      declared, which matters if the valuation is later disputed.

   Authenticity:  Checking whether goods are genuine today means
      querying each brand through its own system.  Here, the officer
      checks that a device's item emblem exists in the brand's own zone
      and validates with DNSSEC, which confirms that the manufacturer
      issued that serial number for that model; a serial that does not
      resolve, or resolves to a different model, is a red flag.  The
      officer must still confirm that the zone really is the brand's
      (lookalike domains are the counterfeiter's obvious move), for
      example against a list of brand domains the customs authority
      maintains.  An emblem alone does not prove that a physical item is
      the one the serial was issued for, since a counterfeiter can copy
      a genuine serial.  Profiles can address cloning by binding a
      device-held key into the item emblem so that the device can prove
      possession when scanned, or by letting the manufacturer flag
      serials reported in implausible places.  This replaces today's
      bespoke per-brand lookup arrangements with one validator that
      works for every brand and every shipment.

   Recycler:  Years later, a recycler scans one device, validates its
      item emblem, walks up to the class emblem, and reads the battery
      chemistry and energy.  It never sees the commercial data, and
      never needs to.

15.3.  Diplomatic Pouches

   Under Article 27 of the Vienna Convention on Diplomatic Relations
   [VCDR], the diplomatic bag may not be opened or detained, and its
   packages must bear visible external marks of their character.  Those
   marks are easy to forge and impossible to verify at a distance, and
   the requirements document describes both the misuse of pouches for
   smuggling and the pressure to inspect them.

   Issuer:  The sending state's ministry of foreign affairs publishes an
      emblem for each pouch under an unguessable label in its own zone,
      using a denial-of-existence method that prevents enumeration
      (Section 9).

   / EMBLEM at k7q2-9xwm-4hd3._pouch._diem.mfa.gov.example /
   {
     "profile":       "diplomatic-pouch",
     "asset":         "k7q2-9xwm-4hd3._pouch._diem.mfa.gov.example",
     "sending-state": "XA",                     / ISO 3166-1 /
     "consignee":     "embassy.xa.example",     / receiving mission /
     "seal":          "XA-2026-114357",   / matches physical seal /
     "pieces":        3,
     "gross-mass":    [4([-1, 184]), "KGM"],    / 18.4 kg /
     "courier":       16(...),       / to receiving state /
     "valid":         [1(1793750400), 1(1794355200)]
   }

   Validator:  The receiving state's customs scans the pouch mark,
      validates the emblem against the sending ministry's zone, compares
      the seal number, piece count, and mass with what is in front of
      them, and decrypts the courier details.  The pouch is never
      opened.

   Proof of presence:  The validated response is evidence that the
      emblem was published and valid when checked.  A customs service
      that wants Level 3 proof of presence ([DIEM-REQS]) records its own
      signed validation event; that record is outside the DNS.

   Removal:  After delivery, the ministry removes the emblem and retains
      it in its archive.

15.4.  Other Use Cases

   The same pattern applies to the other use cases in [DIEM-REQS].  A
   Ramsar-designated wetland would carry a location area and a
   designation endorsed by the Ramsar Secretariat; a CITES shipment
   would carry permit numbers and species codes; an OPCW Schedule 1
   shipment would carry CAS numbers and GHS classifications with
   confidential quantities.  Each is a profile, not a new architecture.

16.  Security Considerations

   DNSSEC provides integrity and origin authentication for emblem data
   only if validators actually validate.  Validators must perform DNSSEC
   validation themselves, or use a resolver they trust over a secure
   channel, and must treat bogus emblem data as absent.  Unsigned emblem
   data must also be treated as absent unless the profile permits
   unvalidated emblems, in which case it carries no assurance of origin
   or integrity.

   An emblem is a statement by a zone holder.  Validators must not infer
   authorization from publication; where a profile requires
   authorization, the validator must validate the endorsement as well.
   Lookalike and typosquatted domains are not addressed by DNSSEC;
   cross-check identifiers and endorsements mitigate them.

   Removal is bounded by signature lifetimes and caching, and passive
   DNS collection means that removed emblems may remain known.  Profiles
   with removability requirements must account for both.

   Encrypted values protect confidentiality, but metadata remains
   visible: the emblem name, the profile, the size of the ciphertext,
   and the timing of queries.  Unguessable labels, with compact denial
   or NSEC3 rather than plain NSEC, reduce enumeration risk.

   Full audits of hierarchical emblems cause many queries; offline
   bundles and caching mitigate this, and profiles should state what
   depth of validation they expect.

   As with physical emblems, displaying a digital emblem may increase an
   asset's risk in some contexts.  Profiles should consider this when
   specifying discovery and removal.

   This document has no IANA actions.  A specification realizing it
   would request the EMBLEM and ENDORSE RRTypes and create registries

Changes from draft-rosenberg-diem-architecture-00

   This section is to be removed before publishing as an RFC.

   *  Adopted DNSSEC as the integrity layer, replacing application-layer
      hashing of emblem records.

   *  Replaced "signed" and "informational" fields with static and
      dynamic facets in separate RRsets.

   *  Replaced the Merkle-tree hierarchy with DNS naming plus cross-zone
      references with optional digests.

   *  Added typed keys and external code lists as value types.

   *  Added endorsement, confidentiality, offline bundles, lifecycle,
      and undetectable validation sections.

   *  Added a strawman EMBLEM encoding using deterministic CBOR.

   *  Added worked examples for IHL, logistics and customs, and
      diplomatic pouches.
